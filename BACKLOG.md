# Personal Financial OS — Backlog

Stories grouped by epic, derived from `ARCHITECTURE.md`. Each story is a checklist item; check them off as they land. IDs (`SETUP-1`, `ING-3`, etc.) are stable references for commit messages, PR titles, or code comments — cheap to reference without a full task tracker.

**TDD convention:** for any story implementing a pure logic function (categorization resolvers, transfer-matching, rollup bucket-tracking, sync pagination), write the test first. Stories that primarily wire a pure function into a queue/route are thin by design and need less test investment than the logic they call.

## Suggested Sequencing

Epics have real dependencies — this is the order that avoids building on top of nothing:

1. **SETUP** — nothing else can start without the monorepo, tooling, and a Docker Compose skeleton in place.
2. **DATA** — schemas and the repository layer come before anything that needs to persist or query data.
3. **AUTH** — `apps/api` needs a real "current user" per request before any route (starting with ING-3's Link routes) can be written correctly (ADR-0018).
4. **ING** — ingestion needs DATA's schemas to write into, and AUTH's `requireAuth` to know whose data it's writing.
5. **CAT** — categorization needs ING's transactions to categorize. _Resequenced 2026-08-31: CAT-7 specifically (the review queue UI) also needs WEB-7/WEB-8 (connect-account flow + a transactions list page) to exist first -- see those tickets. The other nine CAT items are backend-only and unaffected._
6. **XFER** — transfer matching needs CAT's category signals (`TRANSFER_*`) to find candidates. _Correction (ADR-0029): the actual signal is `Transaction.providerCategory`, Plaid's raw field set at sync time -- not any CAT-9 taxonomy value. XFER-2 still chains off categorize-llm's completion to keep the documented pipeline order, not because matching needs Tier 1-4's output._
7. **WEB** — `apps/web` is still SETUP-1's empty stub (package.json/tsconfig/eslint config, no framework, no pages). Bootstrap the application shell -- framework, routing, API client, auth guard, design system -- before any dashboard or review-queue page can be built on top of it. Only depends on AUTH's session contract (ADR-0018) being real, not on ANLY's data existing yet, so it can proceed in parallel with (or right after) the backend work above.
8. **ANLY** — dashboards need ING + CAT + XFER's data (backend) and WEB's application shell (frontend) to be meaningful (cash flow needs `excludeFromCashFlow` from XFER, categories from CAT, transactions from ING, a page to render into from WEB).
9. **SEC** — baseline network/secrets posture belongs in SETUP; the items listed under SEC here are the ones worth deferring slightly (encryption at rest, backups) since they don't block functional development, but shouldn't slip past Phase 1 sign-off.
10. **Phase 2 stories** (`ACCT`, plus new stories appended to `CAT`/`XFER`/`WEB` below) — added 2026-09-01, all net-new feature requests layered on an otherwise-complete Phase 1 (everything above is done except `SEC`). No cross-epic dependency chain like 1-9 above; each new story only depends on what its own epic already built. One sequencing call worth making deliberately: settle `WEB-11` (the redesign pass) before building the other UI-heavy ones (`ACCT-1`, `CAT-11`/`CAT-12`, `XFER-7`, `WEB-9`/`WEB-10`), so new UI gets built once in whatever direction that lands on, not twice.

- [ ] **XFER-7** — Manual transfer review UI — the missing half XFER-4 already flagged ("the manual 'confirm external / pair it' actions this feeds still have no UI to call them from"). Context, since this is the feature the user found confusing: Plaid never links the two sides of a transfer between your own accounts, so the `transfer-matching` job (XFER-1/2/3) looks for opposite-signed, same-magnitude transaction pairs within a date-tolerance window where at least one side carries a `TRANSFER_*`/payment-type signal (`Transaction.providerCategory`, ADR-0029), and auto-links matches via `transferGroupId` + `excludeFromCashFlow: true` so they stop counting as both income and an expense (ARCHITECTURE.md §2.4). This story adds, for a `needs_review` transaction whose `providerCategory` is a transfer/payment-type signal, a choice between "confirm this is a real external transaction" (falls through to the ordinary category correction, CAT-7's existing path) and "link to another transaction" (auto-suggested candidates via the same opposite-sign/close-amount/nearby-date heuristic `findTransferMatches()` already implements, then `TransactionRepository.applyTransferMatch()` on the chosen pair). (2) **Decided (2026-09-01, user confirmed)** — `TransactionRepository.applyTransferMatch(transactionIds, transferGroupId)` takes raw transaction ids with no `userId` scoping at all today, safe only because its one existing caller (the worker job) already operates on a user-scoped candidate pool. The new route must validate against the requesting session's `userId` (`req.session.userId`, `requireAuth`'s existing contract) before it's allowed to touch either transaction — the same `{_id, userId}` pattern `updateCategoryForUser()`/`updateColor()` already use elsewhere in this codebase. Concretely: add `userId` as a parameter and fold it into the `updateMany` filter itself (`{_id: {$in: transactionIds}, userId}`), so an id belonging to another user simply can't match; and _before_ calling it, verify a count of matching documents equals the expected pair size (2), rejecting the whole request (404) if it doesn't — otherwise `updateMany` would silently apply a partial, one-sided match when only one of the two ids actually belongs to the caller, leaving one transaction flagged as a linked transfer with no counterpart. Thread the same `userId` through the worker job's own call site too (it already has it on hand from `findUnmatchedTransferCandidates(userId)`), so this one change closes the gap for every caller, not just the new route.
